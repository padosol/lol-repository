# 챔피언 통계 자동 적재 파이프라인 설계 (PG → GCS → BigQuery)

> 작성일: 2026-10-29 · 상태: 설계 (사용자 검토 대기) · 기준 코드: `origin/develop` @ `c05cb5f`
>
> 2026-10-01 미커밋 초안(`match-stats-incremental-export-design.md`)을 이어받아 대체한다.
> 초안과 달라진 점은 §15 에 모았다.

## 1. 의도

일반 사용자가 챔피언 분석 페이지(op.gg 챔피언 통계와 같은 화면 — 티어·챔피언·패치·라인별 아이템,
스킬트리, 상대 챔피언 전적, 룬, 스펠, 신발, 시작 아이템, 승/픽/밴률)에서 **새로 쌓인 매치가 사람 손 없이
반영된 통계**를 보게 한다.

화면(lol-ui), 조회 API(lol-server, lol-repository `championstats`), BigQuery MV 10종은 이미 있다.
비어 있는 것은 **fact 테이블을 채우는 일**이다. 지금은 사람이 `/internal/backfill/{factType}/run` 을 호출해
GCS 로 export 하고, BigQuery 적재는 코드가 없다(수동 `bq load` 로 추정). 이 문서는 그 구간을
주기 실행으로 자동화한다.

**사용자 결정**
- 범위는 "백필 잡이 자동으로 돌아 BigQuery 에 적재되는 파이프라인" 이다.
- 페이지에 보이는 숫자는 실제 게임보다 **최대 6시간 정도 늦어도 된다.**
- **최신 시즌의 최신 패치만 적재한다** (예: 16시즌 16.21 이 최신이면 16.21 만). 나중에 **최근 N개 패치**로 늘릴 수 있어야 한다.
- **최신 시즌·패치는 패치 테이블(`season`·`patch_version`) 기준**으로 정한다.
- 운영 DB 의 `riot` 스키마 이전은 끝났고 데이터는 새로 쌓고 있다. 파이프라인은 켜도 된다.
- **BigQuery 는 과거 데이터를 모두 지우고 새로 적재한다.**
- `starting_item_exclusion` 테이블은 운영에 만든 적이 없다.

## 2. 목표 · 비목표 · 안티목표

**목표**
- 주기 실행으로 신규 매치의 3종 fact(`match`, `match-ban`, `match-participant-build`) 중 **대상 패치(최신 시즌의 최근 N개, 기본 1)** 행을 BigQuery 에 append
- 게임 종료 → 페이지 반영까지 최악 지연 6시간 이내 (설계상 약 4시간 + 실행 시간)
- 누락 0 · 중복 0 — 재시도, 재배포, 중복 트리거, 적재 직후 장애에도
- 기존 백필 잡, 집계 SQL, MV, 조회 API 를 그대로 재사용

**비목표**
- 화면/API 확장: 시즌·큐 선택, 룬 파편, 4~6번째 아이템, 패치별 추세 (후속 과제)
- BigQuery MV / 조회 쿼리 변경
- 분 단위 실시간 통계
- 과거 시즌·지난 패치 재집계 (필요하면 기존 수동 백필 API). 대상에서 밀려난 패치의 BigQuery 데이터는 그 시점 값으로 남는다.
  부트스트랩에서 과거 데이터를 모두 지우므로 **UI 에서 대상 이전 패치를 고르면 통계가 비어 보인다** — 의도된 결과

**안티목표** — 동작은 해도 이렇게 되면 실패다
- **조용한 중복**: 같은 매치가 두 번 들어가 승률/픽률이 왜곡되는 것. 지연보다 나쁘다.
- **조용한 누락**: 행이 영구히 빠졌는데 아무도 모르는 것. 막히면 멈추고 드러나야 한다.
- **본업 잠식**: export 가 PG 커넥션 풀(운영 10개)이나 CPU 를 잡아 매치 수집이 밀리는 것.

## 3. 현재 상태 (`origin/develop` 기준 사실)

| 항목 | 내용 |
|---|---|
| 백필 잡 | `module/app/application/.../backfill/` — `lolBackfillJob` = `PartitionStep`(ID 범위 청크, 병렬) → `ManifestStep`. 수동 HTTP 트리거, 비동기 launcher(코어 1, 큐 4) |
| export 산출물 | `gs://{bucket}/{factPrefix}/{runId}/chunk_{start:012}_{end:012}.ndjson.gz` + `_manifest.json` (청크 목록·행 수·schema_version) |
| fact ↔ 테이블 | `match`→`match_fact`, `match-ban`→`match_ban_fact`, `match-participant-build`→`match_participant_fact` (dataset `lol_analytics`) |
| 범위 키 | `match.id`, `match_ban.id`, `match_participant.match_participant_id` — 모두 DB 측 `GENERATED BY DEFAULT AS IDENTITY`, CACHE 설정 없음, 앱은 id 없이 JDBC INSERT (`ON CONFLICT DO NOTHING`), 삭제 경로 없음 |
| 저장 순서 | `MatchService.saveAll` 이 match 저장 후 participant/challenges/team/ban 을 별도 스레드(별도 트랜잭션)로 저장, 타임라인도 같은 호출 안에서 `join` — 한 배치의 커밋은 수 초~수 분 안에 끝난다 |
| 필터 | 집계 SQL 은 `:season`(단일) + `:queueIds` 로 거른다. `match.season` = gameVersion 의 major (현재 16). `item_meta` 도 season 별 |
| BQ 클라이언트 | `module/infra/bigquery` 의 `BigQuery` 빈 — `bigquery.credentials-location`(`BIGQUERY_CREDENTIALS`, 운영 `file:/etc/bigquery/bigquery.json`) |
| GCS 클라이언트 | `GcsClientConfig` = `StorageOptions.getDefaultInstance()` (ADC). **운영 파드에는 `GOOGLE_APPLICATION_CREDENTIALS` 가 없다** |
| 운영 env | `BACKFILL_GCS_BUCKET=lol-backfill-local # TODO`, `BACKFILL_SEASON=14`(낡음), range 0/0 — 운영에서 백필이 정상 동작한 적이 없는 상태로 보인다 |
| 조회 서빙 | 운영 Ingress `/api/v1/champion-stats` → **lol-server** (MP-152). lol-repository 이전(MP-179)은 진행 중. 두 서비스가 같은 Redis 를 쓴다 |
| 캐시 | lol-server `champion-stats:v7:detail:*`, `champion-stats:v4:positions:*` / lol-repository `championstats:v1:*` — 모두 TTL 6h, 요청 시 lazy 적재 |
| MV | 10종, `enable_refresh` 30분, `max_staleness` 미설정 → MV 조회 시 base 의 신규 append 분을 BigQuery 가 합쳐 최신 결과를 준다 |
| DB 스키마 | `b894f3a`(10-20) 부터 앱은 `currentSchema=riot` 만 보고, 마이그레이션은 이 레포 `module/infra/persistence/src/main/resources/db/migration/riot/` 가 소유한다 (V1 = 옛 lol-db-schema V1~V35 의 riot 객체 + `item_meta` 기준 데이터, 다음은 V2). lol-db-schema 서브모듈은 제거됐다. **운영 이전 완료, `riot` 에는 데이터를 새로 쌓는 중** (사용자 확인) |
| 스키마 누락 | `match.tier_bucket`(generated) 이 riot V1 에 없다 → 지금 운영에서 집계 SQL 3종이 모두 실패한다. 집계 SQL 이 쓰는 **`starting_item_exclusion` 테이블은 어떤 마이그레이션에도, 운영에도 없다** (사용자 확인) |
| `item_meta` 16시즌 시드 | `LEGENDARY` 255 · `POTION` 16 · `TRINKET` 3(3340·3363·3364). **`BOOTS` 0건** → 그대로면 신발 통계가 빈다. `STARTING_EXCLUSION` 은 14·15시즌에만 있다 (16시즌은 같은 와드가 `TRINKET`) |
| `season`·`patch_version` 테이블 | `season(season_id, season_value)`, `patch_version(version_id, version_value, season_id, patch_version_data)`. `version_value` 는 `match.patch_version` 과 같은 "16.21" 형식 (옛 V35 주석 — 패치노트 표기 26.21 과 다름). 앱은 `version_id DESC` 를 최신으로 본다 (`VersionJpaRepository`). 이 레포에 쓰는 코드는 없다 — 패치 출시 때 외부(수동/lol-server)에서 추가 |
| 패치 표기 | `match.patch_version` = "16.21" 형식, 집계 SQL 이 `patch_version_int = major*100 + minor` (예: 1621) 로 내보낸다. `match.season` = major |
| 스케줄러 패턴 | `@EnableScheduling` + `SummonerRankingScheduler`(`fixedDelay` 2h). Redisson 사용 중 |
| 배포 | k8s, lol-repository `replicas: 1`. 롤링 배포 중 잠시 2개 파드 공존 가능 |

## 4. 전체 흐름

```
 cron (2h, KST :20) ─┐
 POST /internal/stats-export/run ─┤
                     ▼
         StatsExportScheduler ──(Redisson lock "stats-export:lock", 못 잡으면 skip)
                     ▼
         StatsExportService.runTick()
           ├─ 0. 고아 실행 정리 (STARTED 로 남은 lolStatsExportJob 실행 → FAILED)
           ├─ 1. fact 순차: match → match-ban → match-participant-build
           │     ├─ nowMax  = SELECT COALESCE(MAX(id),0)+1          (잡 실행 전 관측)
           │     ├─ range   = [exported_until, observed_until)       (§5)
           │     ├─ range 비었으면 observed_until 만 nowMax 로 전진
           │     ├─ 대상 패치 = 패치 테이블 최신 N개 (범위 첫 시도 때 고정). 범위에 더 새 패치가 있으면 보류 (§6)
           │     ├─ lolStatsExportJob(동기, season + patches) 실행
           │     │     PartitionStep → ManifestStep → BqLoadStep
           │     │         │              │              └─ Load Job (결정적 jobId, WRITE_APPEND)
           │     │         ▼              ▼                       ▼
           │     │   GCS chunk_*.ndjson.gz  _manifest.json   lol_analytics.*_fact ─▶ MV(자동)
           │     └─ 잡 COMPLETED(또는 이미 완료) → 워터마크 조건부 UPDATE
           └─ 2. 이번 틱에 적재 행 > 0 이면 챔피언 통계 캐시 무효화 (§10)
```

원칙: **워터마크는 BigQuery 적재가 성공한 뒤에만 움직인다.** 실패하면 아무것도 움직이지 않고, 다음 틱이 같은 범위를 같은 runId 로 재시도한다.

## 5. 증분 범위 — 워터마크 (1-틱 지연)

### 5.1 테이블 (riot 체인 신규 마이그레이션, §15)

```sql
CREATE TABLE IF NOT EXISTS stats_export_watermark (
    fact_type        VARCHAR(64)  PRIMARY KEY,      -- match / match-ban / match-participant-build
    exported_until   BIGINT       NOT NULL,         -- [.., exported_until) BQ 적재 완료
    observed_until   BIGINT       NOT NULL,         -- 직전 틱에서 관측한 MAX(id)+1 = 이번 틱 export 상한
    range_patches    VARCHAR(100),                  -- 진행 중 범위 [exported_until, observed_until) 의 대상 패치 (예: "1621"), 첫 시도 때 고정·성공 시 NULL
    last_run_id      VARCHAR(128),
    last_success_at  TIMESTAMP,
    updated_at       TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

행이 없으면 서비스가 `exported_until = observed_until = lol.stats-export.seed-id`(기본 0)로 만든다 (§12).

### 5.2 틱 알고리즘 (fact 별)

```
E, O  = 워터마크 (exported_until, observed_until)
nowMax = SELECT COALESCE(MAX(<idCol>), 0) + 1 FROM <table>      -- 잡 실행 '전'에 잰다
if O > E:
    patches = range_patches ?: 대상 패치 결정 후 range_patches 에 저장 (§6)   -- 보류면 이 fact 종료 (워터마크 그대로)
    if patches 비어 있지 않음:
        run lolStatsExportJob(factType, startId=E, endId=O, season=patches/100, patches)   -- runId = inc-{fact}-{E}-{O}
        성공(COMPLETED, 또는 JobInstanceAlreadyCompleteException) 이 아니면 → 이 fact 종료 (워터마크 그대로)
UPDATE stats_export_watermark
   SET exported_until = O, observed_until = nowMax, range_patches = NULL,
       last_run_id = …, last_success_at = now(), updated_at = now()
 WHERE fact_type = :f AND exported_until = :E AND observed_until = :O       -- 낙관적 갱신, 0행이면 경고 로그
```

- **왜 안전한가**: 이번 틱 상한 `O` 는 직전 틱(≥ 2시간 전)에 관측한 값이다. 그 아래 ID 를 받은 트랜잭션은
  `saveAll` 한 호출 안에서 수 초~수 분 내 커밋되므로, 2시간 뒤엔 커밋됐거나 롤백(=ID 공백)됐다.
  match 와 participant/타임라인이 서로 다른 트랜잭션이라 생기는 "ID 순서 ≠ 커밋 순서" 문제
  (participant 는 보이는데 타임라인이 아직 → INNER JOIN 으로 영구 누락)를 스키마 변경 없이 없앤다.
- **전제(불변식)**: ID 가 INSERT 시점에 DB 에서 단조 발급되고, 한 번 발급된 ID 아래로 행이 새로 들어오지 않는다.
  다음은 이 설계를 깨므로 금지한다 — 시퀀스 `CACHE > 1`·Hibernate pooled optimizer 전환, 그리고 **워터마크보다 작은
  ID 로 행을 복사해 넣는 데이터 이전**(`public` → `riot` 를 `INSERT … SELECT` 로 하면서 원래 ID 를 유지하는 경우 등).
  이 전제를 `module/domain/match/CLAUDE.md` 와 마이그레이션 주석에 적어 둔다. riot 이전은 끝났다 (§17).
- **지연 계산**: 주기 2h 일 때 ID 발급 직후 틱 T 가 관측 → T+1(2h) 에 export·적재 → 최악 약 4h + 실행 시간.
  캐시를 적재 직후 비우므로(§10) 6h TTL 이 더해지지 않는다.
- **runId 가 범위에서 결정**되므로 실패한 틱 다음 틱은 같은 JobParameters 로 실행 → Spring Batch 가 실패한
  JobInstance 를 **재시작**(실패 파티션만 재실행)한다. "실패면 restart, 아니면 새 run" 판단 코드가 필요 없다.
- 잡이 COMPLETED 됐는데 워터마크 UPDATE 전에 죽으면, 다음 틱이 같은 파라미터로 실행 →
  `JobInstanceAlreadyCompleteException` → 성공으로 간주하고 워터마크만 전진.

| 대안 | 판단 |
|---|---|
| **1-틱 지연 (채택)** | 스키마 변경 없음, 지연 ≤ 2주기. 2h 주기면 6h 요구 충족 |
| 시간 기반 마진 (`created_at < now()-10m`) | 3개 테이블에 컬럼·인덱스 추가 필요, 마진 근거 약함 |
| 고정 ID 마진 (`max - K`) | K 근거 없음, 트래픽 변동에 취약 |

## 6. 대상 패치 · 큐 (사용자 결정: 최신 시즌의 최근 N개 패치만)

`lol.stats-export.patch-count` = N (기본 1). 대상 패치는 **패치 테이블 기준** (사용자 결정).

```
-- 범위 첫 시도 때만 (range_patches 가 NULL 일 때)
S       = SELECT MAX(season_value) FROM season                                    -- 최신 시즌
targets = SELECT v.version_value FROM patch_version v JOIN season s USING (season_id)
          WHERE s.season_value = S
          ORDER BY split_part(v.version_value,'.',1)::int DESC, split_part(v.version_value,'.',2)::int DESC
          LIMIT N                                                                  -- 최신 시즌의 최근 N개 → patch_version_int 로 변환
rangeMax = SELECT MAX(<patch_version_int>) FROM <fact 테이블> x JOIN match m ...
           WHERE x.<idCol> ∈ [E, O) AND m.queue_id IN (:queueIds)
if S 없음 or targets 비어 있음      → 보류 (ERROR: 패치 테이블 비어 있음)
if rangeMax > max(targets)          → 보류 (WARN: 패치 테이블보다 새 패치 행 존재 — 테이블 갱신 대기)
range_patches ← targets
```

- 예: N=1, 테이블 최신 16.21 → 16.21 만. N=3 → 16.19~16.21 (테이블에 있는 것만). 17시즌 행이 추가되면 17.x 만 (사용자 결정: 최신 시즌만).
- 정렬은 `version_value` 의 숫자 순 — 앱의 `version_id DESC` 와 행이 순서대로 들어왔다면 같고, 순서가 어긋나도 안전하다 (설계자 판단).
- **보류 = 새 패치를 놓치지 않기 위한 장치**: 패치 출시 후 테이블에 새 행이 들어가기 전에 그 패치 매치가 범위에 들어오면,
  그대로 진행할 경우 새 패치 행이 대상 밖으로 영구히 건너뛰어진다. 그래서 그 fact 는 워터마크를 멈추고 기다린다.
  테이블이 갱신되면 다음 틱에 자연 재개되고, 대상은 새 패치가 된다. 보류가 길어지면(2틱 이상) ERROR 로 올린다.
  → **운영 전제: 패치 출시 후 패치 테이블을 늦지 않게 갱신한다.** 늦어지는 만큼 6h 반영 목표도 밀린다.
- **지난 패치를 섞지 않는다**: 갱신(renewal)이 옛 매치를 가져와도 테이블 최신 N개 밖이면 건너뛴다. 대상 밖 행은 의도적으로
  건너뛰고 워터마크는 지나간다 (필요하면 수동 백필).
- **재시도 시 고정**: 범위의 대상은 첫 시도 때 `range_patches` 에 저장하고 재시도는 그 값을 쓴다. 그 사이 테이블에 새 패치가
  들어와 N개 창이 움직여도 같은 범위·같은 파라미터라 Spring Batch 재시작과 BQ jobId 멱등성이 그대로 성립한다 (N≥2 에서 창이
  겹쳐 같은 패치 행이 두 번 들어가는 일을 막는다). 첫 시도 때 보류 검사를 통과했으므로 범위 안에 대상보다 새 패치는 없다.
- `MAX` 조회는 평소 2h 분량 PK 범위 스캔이라 싸다. 패치 테이블 조회는 틱당 1회로 fact 가 공유한다.
- **SQL 변경**: 집계 SQL 3종의 범위 조건에 `AND <patch_version_int 식> IN (:patches)` 를 더한다 (participant-build 는
  `mp_batch` 의 WHERE — 이후 이벤트 조인이 대상 패치 매치로만 줄어든다). 수동 백필은 지금처럼 전 패치를 내보내야 하므로
  패치 필터를 끌 수 있게 한다 (방식은 빌더 재량 — 빈 목록 `IN ()` 은 문법 오류임에 주의).
- **시작 아이템 제외 목록**: 집계 SQL 의 `starting_item_exclusion` 참조를 `item_meta WHERE season = :season AND active
  AND type IN ('TRINKET', 'STARTING_EXCLUSION')` 로 바꾼다 (16시즌은 `TRINKET`, 14·15시즌은 `STARTING_EXCLUSION` 으로 같은 와드 3종이 들어 있다).
- **가드 — 기준 데이터 누락**: `match-participant-build` 는 시즌 `S` 의 `item_meta` 에 `LEGENDARY`·`BOOTS`·
  (`TRINKET` ∪ `STARTING_EXCLUSION`) 중 하나라도 0건이면 실패 처리 — 워터마크 정지 + ERROR 로그 + 메트릭.
  그대로 돌면 아이템/신발 빌드가 빈 채로 적재된다 (안티목표: 조용한 누락). 16시즌 `BOOTS` 는 지금 0건이므로 시드를 추가한다 (§15).
- 큐: `lol.stats-export.queue-ids` (기본 `420`, 솔로 랭크).

## 7. 잡 구성 — `lolStatsExportJob`

수동 백필(`lolBackfillJob`)과 **JobInstance 네임스페이스를 분리**하기 위해 별도 Job 을 만들되, 스텝 빈
(`ChunkExportTasklet`, `ManifestTasklet`, `IdRangePartitioner`)은 재사용한다.

| 스텝 | 내용 |
|---|---|
| `statsExportPartitionStep` | 기존 파티션/청크 export. 청크 크기·병렬도는 `lol.stats-export.chunk.*` (기본 size 50,000 IDs, parallelism 2) |
| `statsExportManifestStep` | 기존 매니페스트 |
| `statsExportBqLoadStep` (신규) | §9 |

JobParameters (identifying): `factType`, `startId`, `endId`, `season`, `patches`, `queueIds`, `mode=incremental`.
`runId` 는 `inc-{factType}-{startId}-{endId}` 로 파생 — 범위의 `patches`·`season` 은 첫 시도 때 고정되므로(§6) 범위만으로 유일하다.

필요한 기존 코드 수정:
- `ChunkExportTasklet` / `ManifestTasklet` 이 `season`·`queueIds`·`range` 를 `BackfillProperties` 에서만 읽는다
  → **JobParameters 우선, 없으면 properties** 로 바꾼다 (수동 백필 동작은 그대로).
- **매니페스트 재시작 누락 수정 (필수)**: `ManifestTasklet` 은 현재 `JobExecution` 의 스텝만 모은다. 재시작 시
  이전 실행에서 COMPLETED 된 파티션은 다시 돌지 않아 현재 실행에 스텝이 없다 → 그 청크가 매니페스트에서 빠지고
  적재되지 않는다(조용한 누락). **같은 JobInstance 의 모든 실행**에서 파티션 이름별 마지막 COMPLETED 스텝을 모으고,
  모은 파티션 수가 파티셔너가 만든 수와 다르면 실패시킨다. 수동 백필도 같은 버그를 갖고 있으므로 함께 고쳐진다.
- GCS prefix 를 `mode` 에 따라 고른다 (§8). `BackfillFactType` 에 증분 prefix 와 BQ 대상 테이블명, 워터마크용
  테이블/ID 컬럼을 추가.
- 증분용 `JobLauncher` 는 **동기**(`SyncTaskExecutor`). 기존 `backfillJobLauncher`(비동기)는 수동 백필 전용으로 둔다.

## 9. BigQuery 적재 — `BqLoadTasklet`

- 매니페스트의 `chunks[].gcsObject` 만 `sourceUris` 로 넘긴다 (와일드카드 금지 — 잔여 파일 혼입 방지).
- `totalRows == 0` 이면 Load 생략.
- 설정: `NEWLINE_DELIMITED_JSON`, `WRITE_APPEND`, `CREATE_NEVER`, 대상 테이블 스키마 사용(자동 감지 안 함),
  `ignoreUnknownValues=false`, `maxBadRecords=0` — 한 행이라도 깨지면 실패하고 드러나게 한다 (안티목표: 조용한 누락).
- **Load Job 1건당 소스 URI 상한 10,000** → 청크가 그보다 많으면 여러 Load Job 으로 나눈다 (part 번호).
- **멱등성 — 결정적 jobId + 시도 번호**:
  ```
  base  = stats_export_{fact}_{startId}_{endId}_p{part}
  for a in 0..9:
      job = bigquery.getJob(base + "_a" + a)
      없음            → 이 id 로 제출 후 완료 대기 → 성공이면 끝, 실패면 예외
      DONE & 성공     → 이미 적재됨, 끝 (재시작/재배포 시 중복 방지 핵심)
      DONE & 실패     → 다음 a
      실행 중         → 완료 대기 후 위 판정
  ```
  실패한 jobId 는 재사용할 수 없으므로 시도 번호로 넘어가고, 성공한 시도가 하나라도 있으면 다시 넣지 않는다.
  같은 jobId 의 중복 거절이 유지되는 기간(문서 확인 필요)은 재시작이 같은 날 안에 일어나는 운영 전제와 충분히 겹친다.
- 클라이언트는 `module/infra/bigquery` 의 `BigQuery` 빈을 재사용한다.
- 로케이션: Load Job 은 dataset 로케이션에서 실행되며 버킷이 같은(또는 포함하는) 로케이션이어야 한다 (§14).

## 10. 캐시 무효화

- 틱에서 적재 행이 1건 이상이면, 모든 fact 처리 후 Redis 에서 `lol.stats-export.cache-evict-patterns` 에 맞는
  키를 `SCAN` + `UNLINK` 로 지운다.
  - 기본값: `championstats:v*` (lol-repository), `champion-stats:v[0-9]*` (lol-server 현행 — 락 키 `champion-stats:lock:*` 는 제외)
  - lol-server 패턴은 Ingress 를 lol-repository 로 돌린 뒤(MP-179) 설정에서 뺀다. 두 서비스가 같은 Redis 를 쓰는 것이 전제다.
- MV 에 `max_staleness` 가 없어 지운 직후 첫 조회가 새 append 분을 포함한다. 동시 미스는 기존 single-flight 가 막는다.
- 위치: `championstats` 컨텍스트에 `EvictChampionStatsCacheUseCase` + `ChampionStatsCachePort` 에 패턴 삭제 메서드를
  추가하고 `module/infra/redis` 어댑터가 구현한다. 스케줄러(app)는 유스케이스만 부른다.

## 11. 트리거 · 동시성 · 장애 복구

- **트리거**: 앱 내 `@Scheduled(cron = "${lol.stats-export.cron:0 20 */2 * * *}", zone = "Asia/Seoul")`,
  `@ConditionalOnProperty(lol.stats-export.scheduler.enabled)` — 운영 기본 `false` 로 배포하고 부트스트랩(§12) 후 켠다.
  수동 `POST /internal/stats-export/run`(즉시 1틱, 202 반환 후 비동기)과 `GET /internal/stats-export/status` 는 같은 서비스를 쓴다.
  나중에 외부 스케줄러(k8s CronJob 등)로 옮길 때는 스케줄러만 끄면 된다.
- **중복 실행 방지**: Redisson `RLock("stats-export:lock")` `tryLock(0, watchdog)` → 못 잡으면 skip.
  롤링 배포로 파드 2개가 겹쳐도 한 쪽만 돈다. 결정적 runId + 낙관적 워터마크 갱신이 2차 방어.
- **고아 실행 정리**: 파드가 잡 도중 죽으면 `BATCH_JOB_EXECUTION.status = STARTED` 로 남아 재시작이
  `JobExecutionAlreadyRunningException` 으로 막힌다. 락을 잡은 직후 `lolStatsExportJob` 의 STARTED 실행(+그 STARTED 스텝)을
  FAILED 로 마감한다 — 락 + 동기 실행이라 "지금 도는 실행"은 있을 수 없다.
- **순차 처리**: 3개 fact 는 순차. 하나가 실패해도 나머지는 진행하고, 실패한 fact 는 다음 틱에 자연 재시도.
- **본업 보호**: export 는 청크당 커넥션 1개를 오래 잡는다 → parallelism ≤ 2 유지 (운영 Hikari 10).

| 상황 | 결과 |
|---|---|
| export 중 장애/재배포 | 워터마크 그대로 → 다음 틱이 같은 runId 로 재시작, 끝난 파티션은 건너뜀 |
| Load 제출 후 완료 대기 중 장애 | BQ 쪽 Load 는 계속 진행 → 재시작 시 같은 jobId 조회로 성공 확인, 재적재 없음 |
| 잡 완료 후 워터마크 UPDATE 전 장애 | 다음 틱 `JobInstanceAlreadyCompleteException` → 워터마크만 전진 |
| 같은 시각 중복 트리거 | 락에서 skip |
| 앱 다운으로 틱 누락 | 다음 틱이 누적 범위를 한 번에 처리 (청크 분할) |
| 패치 테이블이 실제 데이터보다 늦음 | 해당 fact 보류(워터마크 정지) + WARN(2틱 이상이면 ERROR) → 테이블 갱신 후 자동 재개 |
| 기준 데이터(item_meta 등) 누락 / 깨진 행 | 해당 fact 정지 + ERROR 로그 + 메트릭 → 사람이 고치면 자동 재개 |

## 12. 초기 부트스트랩 (1회)

사용자 결정: `riot` 이전은 끝났고 데이터는 새로 쌓는 중이며 파이프라인은 켜도 된다. **BigQuery 는 과거 데이터를 모두 지우고
새로 적재한다.** 옛 적재분과 `riot` 신규 수집분의 중복 문제는 이것으로 사라진다.

1. 운영 선행 조건(§14) 완료 + 마이그레이션 포함 이미지 배포 (스케줄러 `enabled=false`)
2. 3개 fact 테이블(`match_fact`, `match_ban_fact`, `match_participant_fact`)을 **전부 비운다** (`TRUNCATE TABLE`).
   테이블 정의·파티셔닝은 그대로 두므로 MV 는 다시 만들 필요 없이 다음 갱신에 비워진다
3. 워터마크 seed = 0 → `POST /internal/stats-export/run` 2회 (1회차: 관측, 2회차: `riot` 전체 범위에서 대상 패치 export·적재)
4. 페이지 수치 확인 후 스케줄러 `enabled=true`

> 결과적으로 BigQuery 에는 `riot` 에 쌓인 매치 중 대상 패치(최신 N개)만 있다. 이후 패치가 바뀌면 지난 패치 데이터는 그대로 남고
> 새 패치부터 쌓인다.

## 13. 관측

- Micrometer: `stats.export.rows{fact}` (counter), `stats.export.runs{fact,outcome=success|failed|skipped}` (counter),

- 로그: 틱 시작/종료, fact 별 범위·행 수·jobId·소요, 가드 위반은 ERROR (운영 JSON 로그 → Loki)

## 14. 운영 선행 조건 (코드 밖)

1. **운영 GCS 버킷** 생성, `BACKFILL_GCS_BUCKET` 교체(lol-deploy `values-prod.yaml`), `*/incremental/` 30일 삭제 수명주기
2. **버킷 로케이션 = BigQuery dataset 로케이션** (또는 dataset 멀티리전에 포함)
3. **서비스 계정 권한** (`/etc/bigquery/bigquery.json` 의 SA 하나로 통일):
   버킷 `storage.objects.create/get/list`(objectAdmin 또는 creator+viewer), 프로젝트 `roles/bigquery.jobUser`,
   dataset `roles/bigquery.dataEditor`. 코드 측: `GcsClientConfig` 가 ADC 대신 `bigquery.credentials-location` 키를 쓰도록 변경
4. **워터마크 아래로 행을 넣지 않는다**: 파이프라인 가동 후 `public` → `riot` 행 복사 같은 작업은 하지 않는다 (§5.2 불변식)
5. **`riot.match.tier_bucket`**: riot V1 에 없으므로 운영에도 없을 가능성이 높다 → V2 가 `riot.match` 를 재작성(ACCESS EXCLUSIVE)한다.
   `riot` 은 10월 하순부터 쌓은 데이터라 짧겠지만, 그동안 매치 INSERT 가 막히므로 한산한 시간에 배포한다.
   이미 있다면(`\d+ riot.match`) 식이 같은지 확인 — 같으면 `IF NOT EXISTS` 로 건너뛴다
6. **fact 테이블 스키마 진실원천화**: `bq show --schema` 결과를 `docs/data/ddl_*_fact.sql` 로 커밋 (TRUNCATE 전에)
7. **패치 테이블**: 운영 `riot.season`·`riot.patch_version` 에 현재 시즌(16)과 최신 패치(예: 16.21) 행이 있는지 확인.
   이후 패치 출시 때마다 갱신하는 담당·절차를 정한다 (늦으면 파이프라인이 보류된다, §6)
