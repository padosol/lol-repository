# app → method rate limit: 순차 검사 vs Lua 단일 검사 정확도 (2026-11-12)

> 질문: Redis 로 app 한도와 method 한도를 검사할 때, **app → method 순으로 따로 검사**하는 것과 **Lua 로 한 번에 검사**하는 것은 한도를 얼마나 정확히 지키고, 새는(초과 허용·낭비) 슬롯은 없는가?
>
> 코드: `module/infra/riot-client/src/test/java/com/mmrtr/lol/infra/riot/ratelimit/` (테스트 전용 — main 코드는 바꾸지 않음)
> 재현: `./gradlew :module:infra:riot-client:test --tests '*AppMethodRateLimit*'` (Docker 필요, 약 10초)

## 1. 결론

| 방식 | 한도 초과 허용 (새는가) | app 슬롯 낭비 | 공유 app 한도에서 처리량 | Redis 왕복 |
|---|---|---|---|---|
| ① 순차 GET 검사 → INCR (비원자) | **매 trial 발생** (평균 +13~20건) | 없음 | 한도 초과 → Riot 429 | 1~6 |
| ② 순차 app INCR → method INCR | 없음 | **있음** (method 거절 수만큼) | **−16~22%** | 1~2 |
| ③ 순차 INCR + 보상 DECR | 윈도우 안에서는 없음 (경계를 넘긴 DECR 마다 +1) | 최종 0 | **−15~16%** (잘못된 거절) | 2~4 |
| ④ 순차 Redisson RRateLimiter ×2 (현행 라이브러리) | 없음 | **있음** (② 와 같음) | **−16~22%** | 1~2 |
| ⑤ **Lua 한 번에** | **없음** | **없음** | **이상치 그대로 (0%)** | **1** |

- **Lua 만 모든 시나리오·모든 trial 에서 정확했다.** 3개 시나리오 × 20 trial × 2회 실행 동안 허용 수가 이상치와 한 건도 다르지 않았다.
- 키마다 원자인 순차 방식(②·④)은 **새지는 않는다.** 그러나 method 에서 거절된 요청이 이미 app 슬롯을 써 버린다. 그래서 같은 app 한도를 쓰는 다른 method 가 그만큼 굶는다.
- 보상 DECR(③)은 낭비를 되돌리지만 해결책이 아니다. DECR 이 오기 전까지 카운터가 부풀어 있어, 자리가 있는 요청도 거절된다. 동시성이 높으면 손실이 ② 와 비슷하다. 윈도우가 끝난 뒤 DECR 이 도착하면 다음 윈도우가 한도를 넘는다.
- 비원자 검사(①)는 쓰면 안 된다. 동시 64 에서 20/20 trial 모두 한도를 넘었다.

## 2. 비교한 전략

모든 전략은 한 요청마다 `[app 버킷, method 버킷]` 을 **이 순서로** 검사한다. 카운터는 fixed window 다. 첫 INCR 때 PEXPIRE 를 걸어 첫 요청 시점에 윈도우가 시작된다.

| 전략 | 구현 | 동작 |
|---|---|---|
| ① | `NaiveCheckThenIncrLimiter` | app GET → method GET 으로 검사하고, 통과하면 app INCR → method INCR |
| ② | `SequentialIncrLimiter` | app INCR → 초과면 거절 → method INCR → 초과면 거절 (되돌리지 않음) |
| ③ | `SequentialIncrRollbackLimiter` | ② 와 같되, 거절되면 그때까지 INCR 한 버킷을 모두 DECR |
| ④ | `SequentialRedissonLimiter` | 버킷마다 `RRateLimiter` 를 두고 `tryAcquire()` 를 순서대로 호출 (현행 `RateLimitInterceptor` 와 같은 라이브러리) |
| ⑤ | `LuaAtomicLimiter` | 스크립트 하나에서 모든 버킷을 GET 으로 검사하고, 전부 여유가 있을 때만 모두 INCR. 거절하면 어떤 키도 건드리지 않음 |

⑤ 의 스크립트 (`LuaAtomicLimiter.SCRIPT`). 버킷 수에 제한이 없어 app 2개 + method 1개 같은 Riot 형태에도 그대로 쓸 수 있다.

```lua
for i = 1, #KEYS do
    local used = tonumber(redis.call('GET', KEYS[i]) or '0')
    if used >= tonumber(ARGV[i * 2 - 1]) then
        return i                      -- 거절한 버킷 번호
    end
end
for i = 1, #KEYS do
    if redis.call('INCR', KEYS[i]) == 1 then
        redis.call('PEXPIRE', KEYS[i], ARGV[i * 2])
    end
end
return 0                              -- 허용
```

## 5. 해석

- **②·④ 가 새지 않는 이유와 손해 보는 이유.** INCR 과 RRateLimiter 의 `tryAcquire` 는 각자 원자라서, 한 버킷의 허용 수가 한도를 넘지는 않는다. 하지만 "app 통과 → method 거절"인 요청이 app 슬롯을 하나씩 쓰고 끝난다. 이 슬롯은 윈도우가 끝날 때까지 아무도 쓰지 못한다. Riot 으로 나가지 않았으니 429 는 없지만, 그만큼 처리량이 줄어든다. 낭비량은 정확히 "app 통과 후 method 에서 거절된 요청 수"다. method 하나가 막혀 있는 동안 그 method 요청이 계속 들어오면 app 한도까지 커진다 (S1: 50/100).
- **③ 이 낭비 0 인데도 손해 보는 이유.** 보상 DECR 이 오기 전까지 app 카운터는 "처리 중인 거절 요청 수"만큼 부풀어 있다. 동시 64 에서 A 초과 요청이 계속 INCR→DECR 을 반복하면, B 는 실제로 자리가 있는데도 한도 초과로 보고 거절된다. 거절에도 왕복이 2~4회 들어서, 거절이 대부분인 S1 에서는 지연이 가장 길었다. 윈도우 경계를 넘긴 DECR 이 키를 `-1`(TTL 없음)로 만드는 문제도 있다 (3절).
- **⑤ 가 정확한 이유.** Redis 는 스크립트 하나를 다른 명령과 섞지 않고 끝까지 실행한다. 그래서 "모든 버킷 검사"와 "모든 버킷 증가" 사이에 다른 요청이 끼어들 수 없다. 거절할 때는 아무 키도 바꾸지 않으므로 낭비도 생기지 않는다. 왕복이 1회라 지연도 가장 낮은 축이다.
- **지연 수치는 상대 비교용이다.** 로컬 Docker Desktop 의 포트 포워딩과, 풀 10 에 16 스레드가 몰리는 대기가 함께 들어 있다. 절대값으로 읽지 말 것.

## 6. 현행 코드와의 관계 · 권장

- 현행 `RateLimitInterceptor` 는 host 마다 `RRateLimiter` **하나만** 검사한다 (`RateLimitType`: region 460/10s, platform 450/10s). method 한도는 없으므로, 지금 코드에는 이 문서의 "순차 낭비" 문제가 없다.
- method 한도를 더할 때 RRateLimiter 를 하나 더 두고 순서대로 부르면(④), 이번 측정처럼 공유 app 한도에서 16~22% 를 잃는다. 게다가 현행은 `tryAcquire(1, Duration.ofSeconds(3))` 처럼 기다리는 방식이다. 이대로 쓰면 app permit 을 잡은 채 method 를 최대 3초 기다리고, 시간이 지나도 app permit 은 돌아오지 않는다. 이 부분은 코드를 읽고 추론한 것이고, 테스트는 기다리지 않는 `tryAcquire()` 로 쟀다.
- **권장: app 버킷들과 method 버킷을 Lua 스크립트 하나로 검사한다.** 운영에 넣을 때는 다음을 같이 정한다.
  - 거절할 때 `PTTL` 을 함께 돌려주면 `RiotRateLimitException` 의 대기 시간(Retry-After)으로 쓸 수 있다.
  - Redis Cluster 로 옮기면 한 요청의 키들이 같은 slot 에 있어야 한다. 키에 hash tag(`{riot:kr}:app` 처럼)를 붙인다. 테스트 키도 `{rl:<uuid>}:...` 형태다.
  - `EVALSHA` 를 쓰고, Redis 가 재시작해 `NOSCRIPT` 가 나면 다시 로드한다. 테스트는 시작할 때 `scriptLoad` 로 SHA 를 얻었다.

## 7. 한계 (이번 측정 범위 밖)

- **한 윈도우 안의 버스트만 쟀다.** fixed window 경계에서 짧은 구간에 최대 2배가 몰리는 현상은 검사 순서가 아니라 알고리즘의 성질이라 재지 않았다. Redisson `RRateLimiter` 는 sliding 방식이라 경계에서의 동작이 다르다.
- 단일 Redis 노드만 썼다. Redis 장애나 응답 유실(INCR 은 성공했는데 클라이언트가 timeout 난 경우)은 다루지 않았다.
- Riot 응답 헤더(`X-App-Rate-Limit-Count` 등)와 로컬 카운터를 맞추는 문제는 별개다.
