# 갱신 매치 단계 단순화

> 표시: **[결정]** 사용자가 정한 것, **[판단]** 설계자가 정한 것(사용자 확인 전). 판단은 근거와 함께 적는다.

## 1. 왜 하나

- 사용자 요청: 매치 단계(`RenewalMatchStep`)의 흐름을 단순하게 다시 짠다.
- 지금 매치 단계는 할 일이 많다.
  - 선점을 잡고 푼다.
  - 실패한 매치를 매치 적재 큐로 넘긴다.
  - 4xx 실패를 표시하고, 3번 실패한 매치를 대상에서 빼고 백필로 넘긴다.
  - 판정기가 대상이 DB 에 다 들어왔는지 본다.
  - 리스너 안에서 DB 저장을 기다리고, 저장이 실패하면 메시지를 다시 받는다.
- **[판단] 해석:** 사용자 응답을 DB 저장이 아니라 캐시 기준으로 끝내 매치 단계 시간을 줄인다. 앞선 병목 분석에서 매치 단계가 서버 시간의 85~95% 였다.

## 2. 목표 · 비목표 · 안티목표

### 목표
- 4장의 10단계 흐름으로 매치 단계를 바꾼다.
- 사용자 갱신은 Riot 에서 받은 매치를 요청자 캐시에 쓰면 매치 단계를 끝낸다. DB 저장은 기다리지 않는다. **[결정]**

### 비목표
- DB 저장을 확실히 하는 방법. 사용자가 따로 정한다. **[결정]**
- 부른 뒤 실패한 매치를 다시 받기. 누락으로 둔다. **[결정]**
- 계정·리그·소환사 단계, 매치 적재 큐(⑥)·추가 매치 찾기 큐(⑤)의 처리 방식.

### 안티목표 — 돌아가더라도 실패로 본다
- 사용자 응답이 DB 저장을 기다린다.
- 한도를 확인하지 않고 Riot 을 부른다.
- 부르다 실패한 매치 하나가 같은 판 다른 유저의 갱신을 오래 막는다.

## 3. 제약

- **Riot 은 match ids 를 최신순으로 준다.** id 의 숫자가 클수록 최신이다 (예: `KR_8447755703` 이 `KR_8447702916` 보다 최신). 순서를 다시 정렬하지 않는다. **[결정]**
- **허가는 지금의 permit-only 한도 관리자를 쓴다** (`2026-11-11-riot-permit-only-design.md`). `RiotPermitPort.tryAcquire(platform, USER, cost)` 는 남은 칸이 없으면 비어 있는 결과를 돌려준다. 기다리지 않는다.
- **저장은 멱등이다.** 매치·참여자·팀·밴·타임라인 저장 SQL 이 모두 `ON CONFLICT` 다. 같은 매치를 두 번 저장해도 깨지지 않는다.
- **요청자 캐시:** `MatchCacheWritePort.writeMatches(matches, timelines, puuid)` 가 `match:ids:v1:{puuid}`·`match:v1:{matchId}` 를 TTL 3분으로 쓴다. `MatchQueryService` 는 DB 결과 위에 이 캐시를 덮어 보여 준다.
- **갱신 레코드:** 기한 5초(`RenewalRecordRedisAdapter.DEADLINE`)는 그대로다. 단계 비트는 `renewal-mark.lua` 가 합치고, 기한이 지난 뒤 비트가 다 켜지면 늦은 완료로 닫는다. 이 동작은 그대로 쓴다.
- **매치 적재 큐 ⑥ (`mmrtr.matchId.priority`) 처리 순위:** 1 = 나중 타임라인, 2 = 사용자 재시도, 3 = 백필. 사용자 재시도 경로는 매치와 타임라인을 둘 다 받는다.
- **커서:** 갱신이 `SUCCESS` 면 소환사 revisionDate 가 이번 Riot 값으로 옮겨지고, 다음 갱신은 그 시각 이후의 매치만 받는다.
- **컨텍스트 경계(ArchUnit)와 검증:** `./gradlew check` 통과.

## 4. 흐름

메시지 하나(= 갱신 하나)에 대해 차례로 한다.

1. **match ids 조회.** `puuid`, 메시지의 `startTime`, `start` 0, `count` 20. USER 허가 `MATCH_IDS_BY_PUUID` 1건. **[결정]**
   - 허가 거절 → 1초 뒤 같은 메시지를 다시 넣는다. 지금과 같다. **[판단]**
   - 조회 예외 → 지금의 `fetchFailed` 처리(시도 수를 올려 다시 넣거나 실패)를 그대로 쓴다. **[판단]**
2. **20개면 추가 매치 찾기 큐(⑤)에 넘긴다** (`startOffset` 20). **[결정]** 지금처럼 추가 갱신(`lol.renewal.background.enabled`)이 켜져 있을 때만 넘긴다. **[판단]**
3. **DB 확인.** `match` 테이블에 있는 id 를 뺀다 (`MatchRepositoryPort.findExistingMatchIds`). **[결정]**
4. **적재 중 확인.** 선점 키 `renewal:match:claim:{matchId}` 가 있는 id 를 뺀다. **[결정]**
   - 그 매치가 들어오기를 기다리지 않는다. **[판단]** 그 매치는 다른 갱신이 DB 에 저장한 뒤 이 유저 목록에 보인다.
   - 키 값이 이 갱신의 renewalId 면(재전달) 빼지 않는다. 지금 선점과 같다. **[판단]**
5. **순서.** 남은 id 를 Riot 이 준 순서 그대로 둔다. **[결정]**
6. **한도 확인.** **[결정]**
   - 비용: 남은 목록의 앞 3개는 매치와 타임라인(`MATCH` 1 + `MATCH_TIMELINE` 1, 앱 한도로 2건), 나머지는 매치만(`MATCH` 1).
   - 남은 전체를 한 번에 묻는다. 거절되면 절반(올림)으로 줄여 다시 묻고, 1개까지 내려간다.
   - 허가된 묶음은 7단계로 가고, 남은 id 로 다시 전체 크기부터 묻는다. 시도 사이에 기다리지 않는다. **[판단]** 지금 `PermitRounds` 와 같은 방식이다. 지금은 n, n/2, n/4 세 번만 묻는데 1까지 내려가게 바꾼다.
   - 1개도 거절되면 남은 id 를 모두 ⑥ 에 사용자 재시도(처리 순위 2)로 넘기고 갱신 성공 조건에서 뺀다. 백그라운드가 나중에 적재하기 때문이다. **[결정]** 처리 순위 2 는 **[판단]**이다 (처리 순위 1 은 나중 타임라인이 쓴다).
   - 넘기기(발행)가 실패하면 갱신을 실패(`other`)로 끝낸다. 커서가 옮겨지지 않아 다음 갱신이 다시 받는다. **[판단]**
   - 허가 조회가 예외를 던지면 아직 시작하지 못한 id 는 거절된 것과 같이 다룬다. 지금과 같다. **[판단]**
7. **선점.** 허가된 id 를 `SETNX renewal:match:claim:{matchId} = renewalId`, TTL **1분**으로 잡는다. 풀지 않는다. **[결정]**
   - TTL 이 짧은 이유: 선점은 "부르는 중부터 DB 에 들어갈 때까지" 겹쳐 부르지 않으려는 것이고, 그 뒤는 DB 확인(3단계)이 거른다. 부르다 실패한 매치도 1분 뒤면 같은 판 다른 유저 갱신이 부를 수 있다.
   - 4단계와 7단계 사이에 다른 갱신이 먼저 잡으면 그 id 는 부르지 않는다. 받은 허가는 쓰지 않고 버린다. **[판단]**
8. **Riot 호출.** 허가된 묶음마다 매치(와 타임라인)를 바로 병렬로 부르고, 다 시작한 뒤 한꺼번에 기다린다. **[결정]**
   - 매치가 실패(429·5xx·4xx·IO·시간 초과)하면 누락으로 둔다. 큐에 넣지 않고 실패 표시도 남기지 않는다. **[결정]**
   - 매치는 받았는데 타임라인만 실패하면 매치를 저장하고 타임라인은 나중 타임라인으로 넘긴다 (9단계). **[판단]**
9. **캐시와 상태.** 받은 매치와 타임라인을 요청자 캐시에 쓰고, 매치 단계 비트를 켠다. **[결정]**
   - 받은 매치가 0개여도 비트를 켠다. 대상이 없거나 다 누락된 경우다. **[판단]**
   - 캐시 쓰기가 실패하면 갱신을 실패(`other`)로 끝낸다. DB 저장은 그대로 한다. **[판단]**
     - 지금 `MatchCacheWriteAdapter` 는 예외를 삼키고 포트 계약도 "최선을 다함"이다. 실패를 알 수 있게 계약을 바꾼다. 이 포트를 쓰는 곳은 매치 단계 하나뿐이다.
   - 타임라인 없이 받은 매치(앞 3개 밖이거나 타임라인만 실패한 매치)는 ⑥ 에 나중 타임라인(처리 순위 1)으로 넘긴다. 지금과 같다. 없애면 4~20번째 매치의 타임라인을 아무도 받지 않는다. 발행 실패는 경고 로그와 지표만 남긴다. **[판단]**
     - 이 넘기기가 DB 저장보다 먼저 일어나도 된다. 타임라인 테이블에는 FK 가 없고, ⑥ 의 타임라인만 받는 경로는 매치 행 없이도 저장한다.
10. **DB 비동기 저장.** 받은 매치와 타임라인을 저장하되 리스너는 기다리지 않는다. **[결정]**
    - 동시에 도는 저장 수에 상한을 둔다. 리스너 안에서 저장하던 지금은 매치 리스너 수(20)가 자연스러운 상한이었다. 비동기로 바꾸면 그 상한이 없어져 Hikari 풀(로컬 15)을 넘길 수 있다. 상한 값과 방식은 빌더가 정한다. **[판단]**
    - 저장 실패는 로그와 지표로 남기고 다시 하지 않는다 (8장). **[결정: 추후 처리]**
    - 메시지 ack 는 9단계와 저장 넘기기가 끝나면 한다.

## 5. 없어지는 것 [판단]

- **DB 에 있는 최근 매치의 타임라인만 받기.** `RenewalMatchPlan` 의 `withTimeline`과 그 조회(`findMatchIdsWithTimeline`). 3단계에서 DB 에 있으면 빠지기 때문이다.
- **선점 풀기.** `releaseQuietly`, `claim-release.lua`.
- **부른 뒤 실패한 매치 넘기기.** `handOffForRetry` 의 userRetry 부분.
- **4xx 실패 표시와 "3번 실패하면 빼기".**
  - `markFailed`, `findFailedAt`, `findExcluded`, `claim-mark-failed.lua`
  - 키 `renewal:match:failed:*`·`renewal:match:failed-count:*`
  - 지표 `lol.renewal.match_excluded`
- **판정기의 대상 확인.** `RenewalCompletionJudge` 의 대상·DB 확인과 실패 표시 확인을 없앤다. 기한이 지난 `PROGRESS` 갱신을 `FAILED`(`deadline`)로 끝내는 일은 계정·리그에도 필요해서 남긴다. 대상 기록(`recordTargets`, 레코드의 `targets`)도 필요 없어진다.
- **저장 실패 재전달.** `MatchSaveFailure`, `onSaveFailure`, 리스너의 `redelivered` 헤더.

## 6. 앞선 설계에서 바뀌는 곳

| 앞선 설계 | 이 설계 |
|---|---|
| 11-03 원칙 "DB 에 저장한 뒤 ack" | 요청자 캐시에 쓴 뒤 ack. DB 는 비동기 |
| 11-03 5.3 ④ 매치 비트 = 대상이 전부 DB 에 있을 때 | 받은 매치를 캐시에 쓴 뒤 |
| 11-03 5.4 선점 TTL 5분, 저장 뒤·⑥ 으로 넘길 때 푼다 | TTL 1분, 풀지 않는다 |
| 11-03 5.3 ④ 429·예약 실패 → ⑥ 처리 순위 2 | 한도 거절(1개까지 줄여도)만 ⑥ 처리 순위 2. 부른 뒤 429·5xx 는 누락 |
| 11-03 5.4 4xx 실패 표시 → `match_failed` | 누락. 갱신은 성공 |
| 11-03 5.6 3번 실패한 매치는 빼고 백필 | 없음 |
| 11-03 5.5 판정기가 대상의 DB 존재를 본다 | 기한 실패만 본다 |
| 11-03 5.3 ④ 다른 갱신이 선점한 매치를 기다린다 | 기다리지 않는다 |
| `PermitRounds` 시도 크기 n, n/2, n/4 | 1 까지 절반씩 |

## 7. 지표 [판단]

- 누락한 매치 수: 이유(`denied_queued`, `call_failed`, `claimed_by_other`)별 카운터.
- 비동기 저장: 결과별 카운터와 걸린 시간.
- 지표 이름은 빌더가 정하되 지금의 `lol.renewal.*` 규칙을 따른다.

## 8. 알려진 한계

- **부른 뒤 실패한 매치는 이 유저의 갱신으로는 다시 받지 않는다.** 갱신이 성공해 커서가 넘어가기 때문이다. 같은 판 다른 유저의 갱신(선점이 풀리는 1분 뒤부터)이나 백그라운드가 받을 때까지 비어 있다. 4xx 는 계속 빈다.
- **비동기 DB 저장이 실패하거나 저장 전에 프로세스가 죽으면** 그 매치는 누락된다. 캐시는 3분 뒤 사라진다. 사용자가 추후 처리한다.
- **`SUCCESS` 뒤 DB 저장이 끝나기 전에는 목록 첫 페이지 말고는 비어 보인다. [결정]** 캐시를 덮어 보여 주는 곳은 `MatchQueryService.getSummonerMatches` 첫 페이지뿐이다. 그 사이 방금 받은 매치를 열면 상세(`GET /api/v1/matches/{matchId}`)는 404, 타임라인은 빈 값이고, match-ids·daily-count·champions 는 예전 값이다. 평소에는 짧지만 비동기 저장이 밀리면 수십 초까지 늘 수 있다. 상세·타임라인을 캐시에서 읽게 하는 일은 이번 범위가 아니다.
- **다른 갱신이 선점한 매치**는 그 갱신이 DB 에 저장하기 전까지 이 유저 목록에 없다.
- **한도 거절로 ⑥ 에 넘긴 매치**는 5초 안에 들어오기 어렵다. 사용자는 그 매치 없이 `SUCCESS` 를 받는다.
- **DB 저장이 선점 TTL(1분)보다 늦으면** 다른 갱신이 같은 매치를 한 번 더 부른다. 저장은 멱등이라 데이터는 안전하고 호출만 낭비된다.
- **허가를 받은 뒤 선점에 지면** 그 허가는 쓰이지 않는다.
