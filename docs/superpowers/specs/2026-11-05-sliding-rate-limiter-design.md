# Riot 한도 관리자를 ZSET 슬라이딩 창으로 바꾸기

- 날짜: 2026-11-05
- 브랜치: `feat/sliding-rate-limiter` (`feat/renewal-completion` 위, PR base `feat/renewal-completion`) **[판단]**
- 대체하는 것: #135 설계(`2026-10-27-summoner-renewal-pipeline-design.md`) 5.3 의 "초 단위 카운트" 와 6.4 의 "다음 빈 초 예약·활동 표시 키". 버킷 구분·한도 학습·429 정지·Count 안전망은 그대로 이어받는다.
- 표시: **[사용자]** 사용자가 정한 것, **[판단]** 작성자가 정한 것 (빌더가 더 나은 근거가 있으면 바꿔도 되지만 이유를 남긴다).

## 1. 왜 바꾸나

지금 한도 관리자(`riot-acquire.lua`)는 Riot 한도를 **1초 칸**으로 나눠 쓴다. `500:10` 이면 1초에 45칸이다 (`floor(min(500×0.9/10, 500/11))`). 어떤 10초 구간도 1초 칸 11개를 넘지 않으니 Riot 창이 언제 열리든 495 를 넘지 않는다는 근거였다.

이 방식은 안전하지만, 예산을 시간에 고르게 나눠 쓰기만 한다. Riot 이 지키라는 것은 "10초 안에 500건" 뿐이다. 갱신은 원래 몰려서 오는 일이다(첫 방문 갱신 1건 = asia 호출 약 42회가 한꺼번에). 그래서 남는 예산이 있어도 한 초에 45건을 넘으면 다음 초로 밀린다.

asia 허가 시각만 본 시뮬레이션 (첫 방문 갱신 1건 = 42회, 네트워크 지연 제외):

| 상황 | 1초 칸 (지금) | 슬라이딩 475/10.5s |
|---|---|---|
| 한가할 때 5건 동시 | 마지막이 4초 기다림 | 0초 |
| 한가할 때 10건 동시 | 9초 | 0초 |
| 무작위 0.6건/s, p95 | 2.67초 | 1.09초 |
| 무작위 0.9건/s(한계 근처), 5초 안 비율 | 83.1% | 88.1% |

지속 처리량은 두 방식이 거의 같다 (초당 약 45회). 바뀌는 것은 **몰려 올 때의 지연**이고, 이것이 5초 응답 기한에 직접 걸린다.

## 2. 목표 · 비목표 · 안티목표

**목표**
- 아무 W초 구간에서도 허가 수가 `한도 × 안전율` 을 넘지 않는 범위에서, 남는 예산은 바로 쓴다 (버스트 허용).
- 유저 호출이 먼저 나가고 백필은 남는 만큼만 쓴다. **[사용자]**
- 지금처럼 여러 인스턴스가 Redis 하나로 같은 예산을 나눠 쓴다. 시계는 Redis `TIME` 하나다.
- 실험실 판정에서 429 = 0, 10초 구간 최대 사용률 < 1 을 유지한다.

**비목표**
- 지속 처리량을 늘리는 것. 안전율 0.9 를 그대로 두므로 초당 약 45회로 같다.
- 과부하 대책. 실험실 steady(첫 방문 초당 3건 = asia 초당 약 126회)의 기한 초과는 그대로다. Plan 2 의 접수 거절이 맡는다.
- Riot 고정 창의 시작 시각을 헤더로 추적해 그 창에 맞춰 더 몰아 쓰는 것. 정렬을 틀리면 429 가 나므로 하지 않는다.

**안티목표** (돌아가더라도 이렇게 되면 실패)
- 429 가 늘어난다.
- 백필이 유저 버스트 몫을 먹어, 유저 갱신이 지금보다 늦어진다.
- 거절된 요청이 ZSET 에 기록되어 예산이 샌다.

## 3. 사용자가 정한 것 [사용자]

- 레이트리미터는 **ZSET** 으로 만든다. 호출마다 **eventId**(ZSET member), **app 한도**, **method 한도**를 받는다.
- 규칙마다 ZSET 하나를 두고, 사용자가 준 예시 코드처럼 **2단계**로 한다.
  1. 모든 규칙을 검사만 한다 (오래된 항목을 지우고 개수를 센다). 하나라도 넘으면 아무것도 기록하지 않고 기다릴 ms 를 돌려준다.
  2. 전부 통과했을 때만 모든 규칙 ZSET 에 같은 eventId 를 기록하고 0 을 돌려준다.
- 유저 호출이 먼저 나가고, 백필은 남는 만큼만 쓴다.
- **백필은 초당 최대 40회(= 20게임, match + timeline)** 를 상한으로 둔다. 한가할 때도 늘 적용한다. 대상은 BACKGROUND 우선순위 전부(추가 매치 찾기·백필·티어 수집·랭킹 계산)이고 DEFERRED 는 들어가지 않는다. 유저 활동 중의 낮춘 상한(4.3)은 그 위에 겹친다.
- 아래 4장의 우선순위 동작(유저 활동이 있으면 백필 상한을 낮춘다)과 "없어지는 것" 목록은 채팅에서 정리한 내용을 사용자가 "이대로 진행" 으로 승인했다. 초당 40회 외의 구체적인 숫자는 [판단]이다.

## 4. 동작

### 4.1 규칙

- 버킷은 지금처럼 `(routing) × (app | method)` 이다. 이름은 `{routing}|app`, `{routing}|m|{method}` 를 그대로 쓴다.
- 버킷의 한도 헤더에 창이 여러 개면 창마다 규칙 하나다. 예: app `500:10,30000:600` → 규칙 2개.
- 한 호출은 그 routing 의 app 규칙 전부와 그 method 의 규칙 전부를 **모두** 통과해야 나간다.
- method 한도를 아직 배우지 않았으면 method 규칙은 없다 (지금과 같다). app 한도는 배운 값이 없으면 `riot.rate-limit.app-default` 를 쓴다.
- 규칙의 실제 상한 = `max(1, floor(한도 × safetyRatio))`. safetyRatio 는 지금 값 0.9 그대로다. **[판단]** 응답 Count 안전망(한도의 95% 이상이면 1초 정지)과 겹치지 않으려면 0.9 가 맞다.
- 창 길이는 헤더의 W초 그대로 센다. 대신 **응답(또는 실패)을 받으면 그 호출의 기록을 그 시각으로 옮긴다** (4.4). **[판단, 계획 때 바꿈]**
  - 처음 판단은 "허가 시각 그대로, 흔들림은 안전율 10% 가 흡수" 였다. 계획을 쓰다 이것이 틀렸음을 찾았다.
  - 버스트는 한 순간에 몰린다. 허가 시각으로만 세면, 앞 버스트가 조금 늦게 도착하고 다음 버스트가 빨리 도착할 때 Riot 창 하나에 두 버스트가 통째로 들어간다.
  - 예: 450건이 0ms 에 허가되고 20~60ms 에 도착한다. 다음 450건은 그 기록이 빠지는 10,000ms 에 허가되고 10,002ms 쯤 도착한다. 그러면 Riot 창 [20, 10,020) 에 최대 900건이 들어간다. 10% 로는 막지 못한다.
  - 응답 시각은 Riot 도착 시각보다 늘 뒤다. 그래서 기록을 응답 시각으로 옮기면 기록이 빠지는 시각이 "도착 + W" 이후가 되어 겹침이 없다. eventId 가 이 갱신에 쓰인다.
  - 옮기는 것은 Riot 한도 규칙(app·method)뿐이다. 백필 전용 규칙(4.3)은 우리가 정한 상한이라 Riot 도착 시각에 맞출 까닭이 없고, 옮기면 1초 창이 응답 지연만큼 길어져 백필이 초당 `40 / (1 + 응답 지연 초)` 회로 준다. 그래서 허가 시각에 둔다. **[판단, 최종 리뷰 때 바꿈]**
  - 대가로, 지속 처리량은 창이 응답 지연(약 0.1~0.3초)만큼 길어진 것과 같아 약 2% 준다.
  - 실험실의 sliding peak 판정은 가짜 서버가 받은 시각으로 재므로 이것을 직접 확인한다.

### 4.2 허가

- 규칙마다 ZSET 의 각 항목은 허가된 호출 하나다. score = 허가 시각(ms, Redis `TIME`), member = eventId.
- 검사 때 `score ≤ now − 창` 인 항목을 지우고 남은 개수 n 을 센다. `n < 상한` 이면 통과다.
- 넘으면 기다릴 시간 = 앞에서 `n − 상한 + 1` 번째로 오래된 항목(인덱스 `n − 상한`)이 창을 빠지는 시각까지다. 즉 `그 항목 score + 창 − now`, 최소 1ms 다. 규칙 여럿이 넘으면 가장 긴 값을 쓴다.
  - 사용자 예시는 가장 오래된 항목(인덱스 0)을 본다. 상한이 개수보다 작아질 수 있어서(한도가 줄었을 때, 아래 4.3 의 낮춘 상한) 인덱스를 `n − 상한` 으로 바꾼다. **[판단]**
- 통과하면 모든 규칙 ZSET 에 같은 eventId 를 `ZADD` 하고 키 만료를 창 길이로 늘린다.

### 4.3 우선순위

| 우선순위 | 누가 | 상한 |
|---|---|---|
| USER | 갱신 단계, 공개 API 동기 호출, 매치 적재의 사용자 재시도 | 규칙 상한 전부 |
| DEFERRED | 매치 적재의 나중 타임라인 (아직 쓰는 곳 없음) | 유저 활동 중이면 규칙 상한 × 0.8, 아니면 전부 |
| BACKGROUND | 추가 매치 찾기, 백필, 티어 수집, 랭킹 계산 | **늘 초당 40회까지** **[사용자]**. 그리고 유저 활동 중이면 규칙 상한 × 0.5 |

- **백필 전용 규칙 [사용자]:** routing 마다 BACKGROUND 전용 ZSET 규칙 `{routing}|bg` 를 하나 둔다. 창 1초, 상한 40 (`background-max-per-second`)이다.
  - BACKGROUND 호출만 이 규칙을 검사하고 기록한다. app·method 규칙도 함께 통과해야 한다 (4.2 의 2단계에 규칙 하나가 더해질 뿐이다).
  - 안전율은 곱하지 않는다. Riot 한도가 아니라 우리가 정한 값이기 때문이다. **[판단]**
  - 한가할 때도 늘 적용된다. 그래서 백필이 10초 창에 넣을 수 있는 최대치는 400회다. 실험실·운영 app 상한 450 이므로, 첫 유저는 언제 와도 약 50회(첫 방문 갱신 1건분)를 바로 보낸다.
  - 운영 키의 10분 창(`30000:600`, 상한 27,000)에서도 초당 40회면 최대 24,000 이라 안쪽이다.
- **유저 활동 중** = 최근 10초 안에 그 routing 으로 USER 요청이 있었다. USER 요청이 올 때마다(허가 여부와 관계없이) `riot:rl:user:{routing}` 을 10초 만료로 다시 켠다.
- 낮춘 상한은 `floor(규칙 상한 × 비율)` 이고 최소 1이다. 이 값을 4.2 의 상한 자리에 넣는다 (app·method 규칙에만. 백필 전용 규칙은 늘 40). 비율 설정이 [0, 1] 밖이면 그 끝으로 자른다 (1 을 넘는 비율로 규칙 상한을 넘겨 쓰지 않게).
- 낮춘 상한만 막았을 때(모든 규칙이 원래 상한으로는 통과한다) 돌려주는 대기는 `max(1, min(대기, 활동 표시가 끝나는 시각 − now))` 다. 표시가 끝나면 상한이 원래대로 돌아오므로, 낮춘 상한의 자리가 날 때(최대 한 창)까지 기다리지 않고 그때 다시 묻는다. **[판단, 최종 리뷰 때 더함]**
- 그래서 낮에는 백필이 창의 절반까지만 차지해, 유저가 바로 몰아 쓸 여유(asia 기준 약 225회, 첫 방문 갱신 5건분)가 남는다. 한가할 때는 백필이 초당 40회까지 쓴다.
- 이미 나간 호출은 되돌릴 수 없으므로 "유저 먼저" 는 이 여유로만 지킨다. 유저가 몰려 창이 차면 백필은 상한(절반)을 넘었으니 자연히 멈춘다.
- 낮춘 상한은 **모든 창**(운영 키의 10분 창 포함)에 적용한다. **[판단]**
  - 꾸준한 상태에서는 10초 창 규칙과 10분 창 규칙이 같은 조건이 된다: 전체 사용률이 상한의 절반 아래일 때만 백필이 나간다.
  - 다른 것은 백필이 밤새 예산을 다 쓴 직후다. 10분 창이 거의 차 있으면 유저도 그 창에서 빠지는 속도(초당 약 45회)로만 나갈 수 있어 몰아 쓸 수 없다. 이때 10분 창에도 낮춘 상한을 걸어야 백필이 물러나 그 창의 여유가 돌아온다.
  - 대가로, 바쁜 밤 뒤 유저가 들어오면 백필이 최대 약 5분 쉴 수 있다 (예: 27,000 → 13,500 까지 빠지는 시간).
- 숫자(0.5, 0.8, 10초)는 **[판단]** 이다. 설정으로 뺀다 (5장).

### 4.4 기다림과 포기 (인터셉터)

- 인터셉터는 요청 한 건마다 eventId 를 하나 만들고 (UUID) 같은 요청의 재시도 동안 그대로 쓴다. 거절 때는 기록하지 않으므로 같은 member 로 다시 물어도 된다. `RetryInterceptor` 가 다시 보내는 것은 새 요청이므로 새 eventId 다.
- `acquire` 가 0 이면 바로 보낸다. 0 보다 크면 잔 뒤 다시 묻는다.
- **자는 시간 [판단, 최종 리뷰 때 더함]:** `max(대기, retry-min-wait) + uniform[0, 대기 × retry-jitter-ratio]` (기본 25ms, 0.25)를 자되, 누적 대기가 우선순위 상한을 넘지 않게 남은 상한으로 자른다.
  - 대기는 "막은 항목이 창을 빠지는 시각까지" 라, 같은 항목을 기다리던 요청들이 모두 같은 시각에 깨어 하나만 허가받고 나머지는 다시 묻는다. 실험실 steady 에서 이것 때문에 허가 1건에 Lua 호출이 약 46회(1초 칸 방식은 약 3회)였고 초당 최대 7,926회였다.
  - Lua 의 "거절하면 아무것도 기록하지 않는다" 는 그대로 두고, 인터셉터가 흩어 깨운다. 최소 간격은 1ms 단위 대기(창 경계)가 곧바로 다시 묻는 것을 막는다.
  - USER 의 거절 판단은 무작위 몫을 더하기 전 대기로 한다 (`누적 + 대기 > 상한` 이면 자지 않고 거절).
  - limiter 에 물을 때마다 `riot.ratelimit.acquire.attempts{routing,priority}` 를 하나씩 센다.
- 우선순위별 누적 대기 상한은 USER 10초 **[판단]**(지금 앞당김 예약 범위와 같음), DEFERRED 60초, BACKGROUND 30초(지금 값)다.
- **USER** 는 누적 대기 + 이번 대기가 상한을 넘으면 자지 않고 바로 `RiotBudgetExceededException` 이다. 5초 기한이 있어 기다려도 소용없다. 갱신 단계는 지금처럼 잠시 뒤 다시 시도한다(`requeueLater`). **[판단]**
- **DEFERRED·BACKGROUND** 는 위 자는 시간을 남은 상한으로 잘라 자고 다시 묻는다. 상한을 다 쓴 뒤에야 예외를 던진다. **[판단]**
  - 지금 소비자들이 기대는 동작이 이것이다. `MatchFindListener` 는 예외가 기다린 뒤에 오므로 재전달이 곧바로 돌지 않는다고 보고 다시 던진다. `MatchDataProcessor` 는 바로 requeue 한다.
  - 대기가 상한보다 길 때(긴 `Retry-After`, 아래 4.3 의 10분 창 회복) 바로 던지면 재전달·DB 확인·Lua 호출이 쉬지 않고 돈다. 상한까지 자면 스레드 하나당 30초에 한 번으로 줄어든다.
- 예외를 받은 쪽의 처리는 바뀌지 않는다. 갱신 단계는 나중에 다시 시도하고, 추가 매치 찾기는 재전달받고, 백필은 requeue 한다.
- 허가받아 보낸 요청은 응답을 받거나 예외(IO·타임아웃)로 끝나면 `complete(eventId, …)` 로 app·method 규칙의 기록을 지금 시각으로 옮긴다 (4.1. 백필 전용 규칙의 기록은 허가 시각에 둔다). 응답 코드(429·5xx 포함)와 관계없다. Riot 이 받았을 수 있는 호출은 모두 센다. `complete` 가 실패해도(Redis 오류) 응답 처리는 그대로 하고 로그만 남긴다. **[판단, 계획 때 바꿈]**
- 대기가 끝나 보낼 때 `riot.ratelimit.wait{routing,priority}` 타이머에 총 대기 시간을, 포기할 때 `riot.ratelimit.rejected{routing,priority}` 를 지금처럼 남긴다.

### 4.5 정지 (그대로)

- 429 를 받으면 `Retry-After` 동안, 응답 Count 가 한도의 95% 이상이면 1초 동안 그 버킷을 정지한다. 모든 인스턴스가 함께 멈춘다. `riot-pause.lua` 와 `riot:rl:pause:{bucket}` 은 그대로다.
- 새 허가 스크립트는 app·method 정지 키를 먼저 보고, 정지 중이면 남은 정지 시간을 기다릴 ms 로 돌려준다 (모든 우선순위). 기록은 하지 않는다.

### 4.6 한도 학습 (그대로, 읽는 쪽만 바뀜)

- 응답의 `X-App-Rate-Limit`·`X-Method-Rate-Limit` 을 Redis 해시 `riot:rl:limits` 에 쓰는 지금 동작(바뀌었거나 30초가 지났을 때만 쓰기)은 그대로다.
- 사용자 요구대로 한도는 허가 스크립트에 **인자로 넘긴다**. 그래서 Java 가 버킷별 한도를 안다.
  - 이 인스턴스가 응답에서 배우면 바로 반영한다.
  - 다른 인스턴스가 배운 값은 Redis 해시를 다시 읽어 반영한다 (버킷마다 최대 10초에 한 번). **[판단]**
  - 인스턴스는 자기 응답으로도 곧 같은 값을 배우므로, 늦어도 몇 초다.

## 5. 인터페이스 · 키 · 설정

### 5.1 `RiotRateLimiter`

```java
/** 0 = 지금 보내도 된다(기록함). 0 보다 크면 그만큼 기다린 뒤 다시 물어야 한다(기록 안 함). */
long acquire(String eventId, String routing, String method, RiotCallPriority priority);
/** 허가된 호출의 기록을 지금 시각(응답·실패 시각)으로 옮긴다. 기록이 없으면 아무것도 하지 않는다. */
void complete(String eventId, String routing, String method, RiotCallPriority priority);
void learnLimits(String routing, String method, String appLimitHeader, String methodLimitHeader); // 그대로
void pause(String routing, String methodOrNull, Duration duration);                                // 그대로
```

- `NO_CAPACITY`·`YIELD`, `backlogMillis`, `userCallsPerSecond` 는 없앤다. 뒤의 둘은 테스트에서만 쓰였다. Plan 2 의 접수 판단은 새 리미터의 창 사용량으로 다시 설계해야 한다 (Plan 2 몫).

### 5.2 Redis 키

| 키 | 형 | 내용 |
|---|---|---|
| `riot:rl:w:{bucket}:{W}` | ZSET | 규칙 (버킷 × W초 창). score 허가 시각 ms(응답 뒤 응답 시각), member eventId. 만료 W초 |
| `riot:rl:w:{routing}\|bg:1` | ZSET | 백필 전용 규칙 (1초 창, 상한 40). BACKGROUND 만 쓴다. score 는 허가 시각 그대로다 |

옛 키 `riot:rl:c:*`·`busy:*`·`want:*`·`horizon:*` 는 더 쓰지 않는다. 모두 만료가 있어 저절로 사라진다.

### 5.3 허가 스크립트

`riot-acquire.lua` 를 새로 쓴다. 사용자 예시를 바탕으로 정지 확인, 우선순위 상한, 인덱스 계산, 유저 활동 표시를 더한다. 인자 배치는 빌더가 정하되 다음을 넘긴다.
- **KEYS:** 정지 키 2개(app, method), 유저 활동 키, 규칙 ZSET 들. BACKGROUND 면 백필 전용 규칙 ZSET 을 규칙 목록에 더한다 (낮춘 비율을 적용하지 않도록 구분해 넘긴다).
- **ARGV:** eventId, now(테스트용, 비면 Redis `TIME`), 우선순위, 이 우선순위의 낮춘 비율, 유저 활동 만료 ms, 규칙마다 (상한, 창 ms).

`riot-complete.lua` 를 새로 둔다. Java 는 app·method 규칙 ZSET 만 넘긴다 (백필 전용 규칙은 넘기지 않는다). 규칙 ZSET 마다 그 eventId 가 있으면 score 를 지금 시각으로 바꾸고 만료를 창 길이로 늘린다. 없으면 아무것도 하지 않는다 (`ZADD GT` 는 Redis 6.2 이상이라 쓰지 않고 `ZSCORE` 로 확인한다).

`TIME` 뒤에 쓰기를 하므로 `redis.replicate_commands()` 를 지금처럼 둔다. 스크립트 로딩(`LuaScript`, NOSCRIPT 재시도)은 그대로 쓴다.

## 6. 검증

### 6.1 테스트 (Testcontainers Redis, 지금 테스트 구조를 따른다)

리미터:
- 비어 있으면 상한까지 한꺼번에 통과한다 (버스트).
- 상한 + 1 번째는 기다릴 ms 를 받고 기록되지 않는다. 그 ms 가 지나면 통과한다.
- app·method 중 하나만 넘어도 아무 ZSET 에도 기록하지 않는다.
- 창이 둘(10초·600초)이면 둘 다 본다.
- 한도가 줄어 개수가 상한보다 많을 때, 기다릴 ms 가 인덱스 `n − 상한` 항목 기준이다.
- 유저 활동 중이면 BACKGROUND 는 절반에서 멈추고 USER 는 끝까지 간다. 활동 표시가 만료되면 BACKGROUND 는 절반을 넘어 갈 수 있다.
- BACKGROUND 는 한가할 때도 아무 1초 구간에 40회를 넘지 않는다. USER·DEFERRED 는 이 규칙에 기록되지 않고 막히지도 않는다.
- 정지 중이면 모든 우선순위가 남은 정지 시간을 받는다. method 정지는 다른 method 를 막지 않는다.
- 다른 인스턴스(새 limiter 객체)가 배운 한도를 갱신 주기 뒤에 읽는다. 새 인스턴스는 ZSET 을 지우지 않는다.
- `complete` 는 그 eventId 의 기록을 지금 시각으로 옮긴다. 그래서 그 뒤 자리가 나는 시각이 응답 지연만큼 늦어진다. 없는 eventId 는 아무것도 바꾸지 않는다. 백필 전용 규칙의 기록은 옮기지 않는다.
- 낮춘 상한만 막으면 유저 활동 표시가 끝나는 시각까지만 기다린다. 낮춤 비율이 1 을 넘어도 원래 상한에서 멈춘다.
- 지금 있는 학습·NOSCRIPT·Redis `TIME` 테스트는 유지한다.

인터셉터:
- 0 이면 바로 보내고, 양수면 자고 다시 묻는다. 같은 요청 동안 eventId 가 같다.
- USER 는 누적 대기가 상한을 넘을 것 같으면 자지 않고 예외를 던진다.
- DEFERRED·BACKGROUND 는 남은 상한만큼만 자고, 상한을 다 쓴 뒤 예외를 던진다.
- 자는 시간은 최소 25ms 이고, 대기의 25% 까지 무작위로 더하며, 더해도 남은 상한을 넘지 않는다. limiter 에 물은 횟수를 센다.
- 응답을 받거나 예외로 끝나면 같은 eventId 로 `complete` 를 부른다. `complete` 가 실패해도 응답은 돌려준다.
- 429·Count 정지·헤더 학습 테스트는 유지한다.

인수 테스트(`RiotRateLimitAcceptanceTest`)는 "아무 구간에도 상한을 넘지 않는다" 를 슬라이딩 기준(아무 W초 구간)으로 바꿔 확인한다. 가짜 응답에 200ms 지연을 두고(기록을 응답 시각으로 옮기는 경로를 타게), 가짜 서버가 받은 시각 기준 아무 2초 구간에 한도 20:2 의 상한 18(`floor(20 × 0.9)`)을 넘지 않는지 본다.

### 6.2 실험실

1. **기준선을 먼저 잰다.** 지금 리미터로 새 `burst` 시나리오를 한 번 돌려 둔다.
2. **새 리미터로 `run steady`** (기본 5분): 판정 FAIL 0 (429 = 0, sliding peak < 1).
3. **새 리미터로 `run burst`:** 기준선과 비교해 k6 "갱신 끝남 p95" 와 "5초 안 끝난 비율" 이 나아져야 한다.
4. **`burst` 시나리오 (새로):** 한가한 상태에서 일정 간격으로 첫 방문 갱신 N건을 동시에 보낸다. 간격·N·시간은 빌더가 정한다. **[판단]** 30초마다 6건, 5분을 출발점으로 한다. 평균 수요가 처리 한계보다 낮아야 버스트 효과만 보인다. 갱신 사이에 백필이 초당 40회로 도는 것도 이 시나리오에 들어간다 (첫 방문 갱신마다 20게임 이후 매치가 백필로 넘어간다).
5. Grafana·Prometheus 로 백필(BACKGROUND) 호출이 아무 1초에도 40회를 넘지 않았는지 본다 (`riot.ratelimit.wait{priority="BACKGROUND"}` 수의 1초 증가량).
6. 실험실 README 의 "1초에 45건으로 나눠 쓴다" 설명을 새 방식으로 고친다.
7. **`burst` backlog 변형 (최종 리뷰 때 더함):** `BURST_INTERVAL=15 BURST_ROUNDS=20`. 기본 `burst` 는 버스트 하나의 asia USER 호출(144)이 유저 활동 중 백필이 남긴 225 안에 늘 들어가 유저가 백필과 자리를 다투지 않는다 (사용률 0.450 = 225/500). 이 변형은 백필이 다 빠지기 전에 다음 버스트가 온다. 지금 리미터와 새 리미터로 한 번씩 돌린 결과는 실험실 README "한도 관리자 비교" 에 있다.

## 7. 위험과 한계

- **절벽.** 창을 몰아 쓴 직후 다음 요청은 최대 한 창(10초)을 기다릴 수 있다. 지금 방식은 이 대기를 고르게 퍼뜨린다. 과부하에서는 두 방식 모두 줄을 서므로 차이가 없다.
- **유저끼리 순서 없음.** 기다리던 USER 들은 무작위 몫(4.4)만큼 흩어져 깨어 다시 묻는다. 먼저 기다린 요청이 먼저 나간다는 보장은 없다. 갱신마다 5초 기한이 있어 문제 삼지 않는다.
- **배포 중 섞임.** 운영 `develop` 은 1초 칸 키가 아니라 Redisson `RRateLimiter` 로 세는 `RateLimitInterceptor`(키 `external:api:region` 460/10초, `external:api:platform` 450/10초)로 돈다. 옛 파드는 새 ZSET 을 함께 세지 않고 `riot:rl:pause:*` 정지도 따르지 않는다. 그래서 부하가 있을 때 옛 파드와 새 파드가 섞여 돌면 각자 자기 상한까지 보내 합계가 Riot 한도를 넘고, 새 파드만 멈추므로 429 가 이어질 수 있다. Count 안전망·429 정지는 새 파드만 받친다.
  - 대책: 배포 전략을 Recreate 로 하거나, 옛 파드를 먼저 0 으로 줄인 뒤 새 파드를 띄우거나, 트래픽이 적을 때 배포한다 (`2026-11-03-renewal-completion-design.md` 7장 "배포 전 운영 작업").
- **Redis 데이터 유실 (같은 위험의 두 번째 계기).** Redis 가 데이터를 잃으면(재시작, 장애 조치, FLUSH) 규칙 ZSET 과 `riot:rl:limits` 가 함께 사라진다. 그러면 다음 창은 빈 채로 시작해 상한 전부(예: 450)를 한꺼번에 보낼 수 있는데, Riot 창에는 직전 호출이 그대로 남아 있다. method 한도도 첫 응답으로 다시 배울 때까지 모르므로 그동안 method 규칙이 없다. Count 안전망·429 정지가 받친다.
- **메모리.** 운영 키 10분 창(30000:600)이면 routing 마다 ZSET 항목이 최대 약 2만 7천 개(약 수 MB)다.
- **허가와 도착의 차이.** 기록을 응답 시각으로 옮기므로(4.1) 끝난 호출은 Riot 도착보다 늦게 센다. 아직 응답을 기다리는 호출만 허가 시각으로 남는데, 읽기 타임아웃(5초)이 창(10초)보다 짧아 창 안에 들어 있다. `complete` 가 Redis 오류로 실패한 호출은 허가 시각으로 남아 조금 일찍 빠질 수 있다. 안전율 10% 와 Count 안전망이 받친다.
  - 이 논리는 창이 가장 긴 응답 대기(연결 3초 + 읽기 5초 = 8초)보다 긴 규칙에만 맞는다. 개발 키 `20:1`(`riot-local.yml`)의 1초 창처럼 짧은 창에서는, 응답이 창보다 오래 걸린 호출의 기록(허가 시각)이 응답 전에 창을 빠져 다음 허가가 나가므로 Riot 창에서 여전히 겹칠 수 있다.
- **새로 배운 창은 빈 채로 시작한다.** 기동 직후 기본값(`500:10`)만 알다가 첫 응답에서 `30000:600` 을 배우면, 10분 창 ZSET 은 그 뒤 호출만 센다. 기동 직후 몇 분 동안은 Riot 이 센 것보다 적게 볼 수 있다. Count 안전망이 받친다.
